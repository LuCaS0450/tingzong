# Supabase 持续磁盘 I/O 修复（2026-10-29）

状态：已清除已定位的持续负载，并验证维护脚本的防复发处理。官方突发额度余额未读取到；余额回充取决于平台，不能把短时修复验证表述为永久不会再发生资源告警。

## 根因与证据

- 项目 `bbzpffucjicfnpfzeoqq` 的查询性能统计保存了 60 条超过64 KiB的历史维护语句，主要是内联目录载荷的 `DO $playlist$ ...`。统计 SQL 文本合计82,566,381字节，单条最大2,507,518字节。
- PostgreSQL 不会像普通 SELECT 那样规范化顶层 DO 内部的字面量。读取 `pg_stat_statements` 视图会返回这些完整文本，受2,184 KiB的 `work_mem` 限制产生约83 MB的临时物化文件；修复前后台累计临时文件持续增长。
- 旧报告的约1.2 TiB临时写盘是从2026-09-29起的累计值，不能直接认定全部由近期备份引起。`seq_scan` 也不等于物理磁盘读取；本轮发现时 `v2.scenes.heap_blks_read=0`。033的16个索引有效，但没有处理统计文本膨胀。

## 已实施

1. 通过 `scripts/cloud_sql_runtime.py` 处理大于64 KiB的顶层DO：以普通SELECT把完整语句传给同会话、调用者权限的临时函数执行。外层事务、保存点、异常回滚和DO输出保持原有行为；现有 Session Pooler连接沿用。
2. `cloud_backup.query` 统一使用此处理，现有维护调用方直接受益。常规SQL保持原样。性能计数采样使用 `extensions.pg_stat_statements(false)`，避免反复物化SQL正文。
3. 全量云备份CLI增加必填 `--reason`，记录对应操作原因；AGENTS与V2_SETUP明确日常开发复用有效恢复点，移除不分风险套用完整备份流程的解释。
4. 22:47:33（上海时间）归档2141条查询性能记录后，执行一次 `extensions.pg_stat_statements_reset()`，释放膨胀的统计文本。只清理查询性能诊断历史，未重置 `pg_stat_database` 累计计数，也未修改业务数据或全局内存参数。

诊断原文和计数保存在本机私有文件 `.private/diagnostics/disk-io-20261029T144727Z/query-statistics.csv`，文件可读并逐条JSON解析验证，共94,091,250字节；不要复制到公开源码或APK。根因证据及只含必要数字的采样记录为 `artifacts/disk-io-fix-20261029.json`。
